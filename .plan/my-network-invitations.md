# My network: received connection requests (see them, Accept or Ignore)

- Status: locked; slice 1 (the UI) built and seen in a browser; slice 2 (the task) built, tested against fixtures and a stand-in page, and read-only run live once on tripti.verma (2026-10-27, DONE, 5 requests); no answer has been clicked live yet; slice 3 (brain and the live page) built and tested, not run end to end in a browser against a real account

## Goal

The owner sees the connection requests an account has received, and answers each one (Accept or Ignore) from a new page, "My network", without opening LinkedIn. A good run reads the list and answers only what the owner chose, each at most once, at a human pace. A bad run says plainly what did not happen (signed out, request gone, not sure) and never answers twice. The UI comes first, on sample people; the spider task and the brain follow.

## Requirements

Confirmed by the owner, 2026-10-27:

- A task that reads the received connection requests and takes an action on them: Accept and "reject" (LinkedIn's word is Ignore).
- The UI/UX called "My network" is built first.
- The word is "Ignore"; v1 is manual only (no auto-accept rules); the list is read on demand only (no scheduled read).
- Kept about each request: name, slug, headline, mutual-connection line, the sender's note and the photo. There is no deletion policy for now (rows stay until the account is deleted, which cascades); this is a known privacy gap, listed in Edge cases and `MEMORY.md`.
- Limits: at most 10 answers per run, 50 per account per 24 hours, 4 to 9 seconds between two clicks, one run at a time per account, the browse budget as for other tasks, and a "Start anyway" override after a budget refusal (the same dialog as the accounts page).
- Live test accounts: `tripti.verma@elitale.com` (read first, then one real answer) and `shreechand.sushi@gmail.com` for a second layout.
- Names: route `/network` (optional account id), sidebar "My network", page title "My network", task `linkedin-invitations` (permanent).

Open questions: none.

## Scope and non-goals

- In scope: the page; one spider task that reads and answers; brain tables, service, router and import job; limits; tests; the cron monitor label if a job is added.
- Out of scope (later, separate plans): sending connection requests, withdrawing sent requests, the Sent and Connections tabs, "Catch up" (birthdays, job changes), auto-accept rules or a workflow block, scheduled reads, an all-accounts view, replying to the sender's note, keeping our own copy of the photo (the page shows the address LinkedIn gave; when it expires the initials show).

### Slice 2: the spider task `linkedin-invitations`

One task, two jobs in one browser session: read the list, and answer the chosen requests. Reading is always done, so an answer run also returns the fresh list. Input (`version` 1): `{ answers: [{ id: digits (15 to 25), action: 'ACCEPT' | 'IGNORE' }] }`, at most 10, empty = read only. Result: `invitations.json` file attached with `context.attach` (schema in `packages/contracts/src/invitations.ts`: `readAt`, `total` from the heading, `complete`, `invitations[{ id, slug, name, headline, mutual?, note? }]`, `outcomes[{ id, action, outcome }]`), plus a verdict and a fixed sentence. Verdicts: `DONE` (read, and every asked answer ACCEPTED or IGNORED), `PARTIAL` (read; some answers GONE, UNSURE or not clicked), `UNKNOWN` (a click may have landed and the page does not say; never retried), `SIGNED_OUT`, `ERROR`. Per-request outcomes: `ACCEPTED`, `IGNORED`, `GONE`, `UNSURE`, `NOT_CLICKED`. Budget `{ estimateS: 120, class: 'ACTION' }` when asked by the owner (the reader is the same page), `policy.oneAtATime: 'account'`, `recording: { always: true }`.

Run, after the runner's own lifecycle (starts on a signed-in feed):

1. `visit` `/mynetwork/invitation-manager/` (the preview on `/mynetwork/grow/` shows only 3); check the landed page with `isSignedOutPage`; wait in a bounded loop for rows or the "nothing pending" state (a page can take 15 to 30 s through the proxy; never call it empty early); scroll for more up to 100 rows, `complete: false` when capped.
2. `parseInvitations(html)` (pure reader in `linkedin/invitationReader.ts`, fixture in `linkedin/invitationFixture.ts`).
3. For each asked answer in order: the row must still be on the page (else `GONE`); `markAttempt()` is asked once, before the first click of the run (false: `UNKNOWN`, nothing clicked); click the row's button through `hands.clickSelector` with a selector built from the validated id (`[componentkey="urn:li:invitation:<id>"] button[aria-label^="Accept"]`, plain CSS); wait in a bounded loop for the confirmation card or the row leaving; pause 4 to 9 s; after an unclear outcome stop answering (`UNSURE`, the rest `NOT_CLICKED`) so a problem is not repeated.
4. Read the list again, build the file, answer.

Selectors live in `linkedin/markup.ts` with the date and account. Non-English accounts are not handled: the two labels are words, so the rows would not match and the task ends `ERROR` rather than clicking by position (listed unverified; the account language follows the proxy exit).

## Edge cases and risks

- A request is withdrawn or answered on the phone between the read and the click: the row is not on the page, outcome `GONE`, not an error.
- The click may have landed but no card shows (slow page): `UNSURE`, the run stops answering, the owner reads again to check; never a second click. A redelivered command finds `markAttempt` false and clicks nothing.
- Same request chosen twice or in two tabs: a single QUEUED row per request, the second answer is refused with "Already being answered".
- The list is longer than one read (cap 100): `complete: false`, nothing is marked GONE from that read.
- Requests that are not people (pages, newsletters, events) or a layout the reader does not know: skipped, never clicked; counts may differ from the heading, the file keeps `total` next to what was parsed.
- Non-English account, a second layout, a changed label: no match, `ERROR` with a fixed sentence and the kept `failure.html`; no positional guess.
- Sign-in page, security check, restriction after an answer: `SIGNED_OUT` or the runner's verdict; the session is not saved from a sign-in page.
- Slow or refused by the budget (office hours, gap, day full): the row stays Waiting, the owner sees brain's sentence and may Start anyway after saying they understand the risk (it bypasses only the browse budget, never the 10 per run or 50 per day caps).
- Pace: accepting many people quickly is a pattern LinkedIn may watch; the caps and gaps are conservative guesses, not published limits, and the owner can lower them. Building this is for the owner's own account and requests, in LinkedIn's usual flow.
- Privacy: other people's names, headlines, notes and photo addresses are stored about third parties with NO deletion policy for now (the owner's decision, 2026-10-27): rows live until the account is deleted. A policy (age limit, erase by slug on request) is a follow-up and an open item in `MEMORY.md`. Never logged, never in task messages; the run video and `failure.html` can show them (already true for messages, 7 days, private bucket). The photo address is a LinkedIn link that expires; the page shows it with `referrerPolicy="no-referrer"` through `Mark` and falls back to the initials.
- Injection: ids are digits only (checked in the contract and again in the task) before they enter a selector; nothing from the page is put in a selector.
- Existing data and migrations: additive only, no reset; the new table is empty at first. Rollback: stop the page link and the task; the tables can stay.
- Dev vs production: the spider worker must be restarted to announce the task; staging needs the migration and new brain, worker and spider images; `BROWSE_BUDGET` on in production.
- UI before backend: the sample banner must disappear in slice 3, and no page text may claim an answer was sent while the sample source is used.
