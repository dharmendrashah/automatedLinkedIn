# One client: remove the client logic of LinkedIn accounts

- Status: done <!-- draft | locked | in progress | done -->

- Locked by user: yes, 2026-11-02 <!-- change to "yes, <date>" only after the user confirms -->

## Goal

The rule is **1 client, 1 login, 1 user**: the user is the client. There is no separate client, no client chosen for an account, a list, a person, an invite or a spend line, and no client on any screen, workflow block, setting, address or API call. Remove the whole client concept: the account's Client select and Client text, the client pickers, "All clients", per-client spend views, the `client` setting of workflow blocks, the account-to-client routing, and then the `Client` table and every `clientId` column. My network, invites, lists, workflows and spend work for the owner as one workspace.

## What exists today (checked in the code and the two local databases, 2026-11-02)

- **Schema** (`apps/brain/prisma/schema.prisma`): `Client` (per owner, one `isDefault`, `seenAt`); `clientId` on `LinkedInAccount` (nullable, null means the default client), `WorkflowList` (nullable), `LinkedInProfile` (the targets, nullable), `DataRead` and `SpendLedger` (nullable), `Person` (required, unique `[clientId, slug]`, ten indexes lead with `clientId`), `LinkedInInvite` (required, partial unique index of one live invite per client and person), `PeopleExport` (required). `LinkedInAccount.clientLabel` is an older free-text client name used for the list tag, the Accounts search and the Activity roll-up. Triggers `people_index_by_account` and `people_index_by_list` mark people dirty when a `clientId` changes.
- **Brain** (45 files, 18 of them tests): `ClientService` (`defaultId`, `list`, `create`, `rename`, `assignAccount`, `owned`); `PeopleService` (`ALL_CLIENTS`, `scopeOf`, every list, count, filter, result, seen, bulk change and export takes a `clientId`); `PeopleIndexService.refresh` (`clientOf`: account to client); `LinkedInInviteService` (`accountsOf(userId, clientId)`, invites queued per client); `InputPeopleService.scope`; `DataReadService` and spend (`clientId` books a read to a client); `CollectKeepService`, `PostAuthorService` (default client); resolvers `people.clients`, `createClient`, `renameClient`, `assignAccount` and `clientId` inputs on most `people.*` procedures; the `client` setting of the `input.profiles` block.
- **Body** (40 files, 7 of them tests): `account-client.tsx` (account drawer Client select), `drawer-browsing.tsx` and `browsing/client-field.tsx` (Client text), `accounts-toolbar.tsx` and `toolbar.ts` (Accounts client filter), `roll-up-csv.ts`, Activity by client (`accounts-drawers.tsx`, `bulk-browse-bar.tsx`, `use-account-edits.ts`), My network (`address.ts` `ALL_CLIENTS`, `pickers.tsx` with New client and Rename client, `Network.tsx`, `people-table.tsx` client chip, filters, invite and add-people dialogs, `use-seen-on-leave.ts`), `company-people.tsx`, `person-view.tsx`, the Posting page's client labels (`landing.ts`, `use-client-labels.ts`), `Usage.tsx`, and workflow blocks (`client-pick.tsx`, `network-filters-field.tsx`).
- **Data**: local database `postgres` has 4 clients for 3 owners, 13 accounts (1 with a client), 10,016 people, no person in more than one client, 3,617 spend ledger rows; `automatedlinkedin` has no clients. Staging is not checked.
- **Earlier decisions this reverses**: "one client per account" and "clients are real and separate" (`.plan/network-hub.md`, 2026-10-30), "My network opens on All clients" (`.plan/network-all-clients.md`, 2026-10-31), the shared wallet with a monthly per-client ledger (2026-10-17).

## Requirements

Confirmed (from the request and the owner's answers, 2026-11-02):

- All accounts belong to one client; the client logic of LinkedIn accounts goes.
- **1 client, 1 login, 1 user** (owner's rule, 2026-11-02): every login is one `User`, that user is the whole client, and nothing in the product models a client apart from the user. Everything is already scoped by `userId`; this plan removes what sits beside it.
- **The Platform Admin role stays** (owner, 2026-11-02): `User.role` and the admin-only pages (cron monitor, usage) are about running the service, not about clients.
- **Persona agents are updated** to the one-client rule: `.github/agents/user-agency-owner.agent.md` and `.github/agents/user-platform-admin.agent.md` (several paying clients, spend per client) and any other agent or instruction line that says "clients" in that sense (step 8).
- **Workflow logic and blocks are in scope**: the `client` setting of Profiles blocks (`inputPickSchema.client`, the `client` field kind and `ClientPick`), the My network filters field and its client pick, `InputPeopleService` (`NetworkPick.clientIds`), the output list's `WorkflowList.clientId`, run input and templates that name a client, and API descriptions. The engine and the Account Actions blocks have no client code of their own (checked: none in `worker/engine`).
- **Depth: both parts in one change.** First the data is collapsed into one client, then the `Client` table and every `clientId` column are dropped (a destructive migration; the owner chose it knowingly).
- **People in several clients** are merged into one row: the furthest status (Replied over Contacted over New; Not interested and Done kept if any client chose them), labels joined, notes joined with a line between, Do not contact if any client set it, the oldest first seen.
- **Spend**: the per-client views and per-client month totals go; spend is the owner's, one line per month; past amounts are kept (rows of the same month are added together).
- **The Client text on accounts (`clientLabel`)** is removed everywhere: account drawer, Accounts search, the Activity roll-up by client, bulk edit, the CSV column, the list tag, the Posting page labels.
- **Do not contact** becomes one: the person flag and the `Suppression` row stay as they are, the two-choice wording (for this client, for every client) goes.
- **Saved workflows**: the `client` setting of Profiles blocks is removed and a saved value is ignored.

## Scope and non-goals

- In scope: the steps under Approach: a data migration that collapses every owner to one client, a schema migration that drops `Client` and every `clientId`, the code and screens that used them, tests, `MEMORY.md`. One new column keeps what lived on the client: `User.peopleSeenAt` (from the default client's `seenAt`, for the "new since you last looked" mark of My network).
- Out of scope: changing what an account can do; the Platform Admin or any team features; spider (no client references there).

## Edge cases and risks

- **Destructive data step.** The migrations delete clients, merge people and then drop a table and columns; none of it can be undone from the app, and what the drop removes (client names, `clientLabel` text, the per-client split of past spend) is gone for good. Mitigation: a `pg_dump` of every database before it, the dry run on a scratch clone, counts compared before and after, rollback is restoring the dump. The repository rule is that migrations are additive; this one is not, so it is applied locally now and to staging only when the owner says so at release time.
- **Person merge collisions.** The unique `[clientId, slug]` is satisfied only after the duplicates are merged; the merge must run before the move, and links that point at the removed rows must follow. A partial unique index on live invites must not be broken by the move (cancel the younger live invite first).
- **Staging data is unknown.** The migration must run on its own data without a human check, so it only merges by the stated rule, logs the counts it changed, and never fails on a missing default client (it creates it).
- **People index.** Migration A sets every person's client in the migration itself, and migration B removes the column, so the page is right at once; the rebuild only refreshes derived fields (the `people-index` job drains 200 a pass; 10,000 people is about 50 passes). The SQL functions and triggers that name `clientId` must be rewritten in migration B, or the first write after it fails.
- **Old links and saved state.** Bookmarked `?client=` and `/network/<account>` addresses, saved views and saved workflow settings that name a client must keep opening; unknown values are ignored.
- **Invites in flight.** Queued or sending invites keep their account; only the client column moves. The send job reads the account's client through `dropUnwanted`: after the move it compares equal for everyone. A `SENDING` invite is not touched.
- **Spend and the wallet floor.** Booking by client goes; the wallet balance and the floor check are unchanged. A test proves a read is still booked and totals per month equal the old sum across clients.
- **Concurrency and rollout.** Migration B drops columns the old brain reads, so old pods fail until the new ones run. Run the `migrate` job, then roll brain and worker together, in one release; never run old and new code against the migrated database. In Prisma 7 `migrate dev` does not regenerate the client: run `db:generate`, and use `pnpm ts:check --force` because the generated client is not body's cache input.
- **Persona and product.** The Agency Owner flow (one list per client, spend per client) is gone by design; it is recorded in `MEMORY.md` so a later request for it is a new decision.
- **Docker and CI.** No new env, image or workflow change; CI runs unit tests only, so the migration is checked locally through the integration run and the scratch clone.
- **Dev vs production.** Local `automatedlinkedin` has no clients (nothing to move); local `postgres` has data and is the dry run; staging gets the migration with the next deploy.
