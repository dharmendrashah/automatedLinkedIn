## Goal

A Starter campaign on staging has found 0 people after about two weeks, so the Invite, Warm up, First message and Hand off workflows never start. Make a Discover run that finds people put them on the campaign and into the next workflows.

Full evidence and the three options for each decision: [.plan/egm/campaign-finds-nobody_design_draft.md](egm/campaign-finds-nobody_design_draft.md).

## Requirements

Confirmed by the owner:

- The campaign's Found count and the later workflows must read the campaign label (today they read `Person.labels`, which Discover never writes).
- The Starter keeps its six workflows and names; all stay switched off until the owner switches them on.
- Decision 1 (2026-11-10): Option A, write-through to `Person.labels`: the tags of each kept person are added to that person's labels, and a removal from the list does not remove the label. Option A is confirmed; its stage scope is the one open question.
- Decision 2 (2026-11-10): Option 1, Discover reads each commenter's and reactor's profile before its single Score.
- Owner freedom (2026-11-10): new blocks and changes to existing blocks are allowed when they make the campaign find and act on leads faster, smarter and reliably on staging.
- Changes are additive; no database reset.

Derived by the review (rounds 1 to 4 of 2026-11-10):

- R-A1 (writers): two places, both only for runs of a campaign workflow (`ctx.run.workflow.campaign` is set, `workflowRun.service.ts`). (a) `process.tag` labels the people it passes that already have a `Person` row (`build: false`); the rest are counted. (b) `output.list` (`addToList`), after `WorkflowListService.addFromRun`, refreshes and labels the slugs `addFromRun` inserted (`build: true`). Discover's Add label runs before the list step inserts its members, so the list step labels its people. The people index is not a label writer and runs outside campaigns are unchanged.
- R-A2 (rule): the run's tags are appended after the person's existing labels. Existing labels are never removed or capped (a person may already hold more than 20 manual labels). Only the appended tags are capped: distinct, first-seen order, at most `LABEL_MAX` (20) minus the existing count, never below zero. A tag that does not fit is dropped and counted. Messages: `process.tag` adds "N people have no row yet; they are labelled when they are listed." when N > 0; `addToList` appends "N labels did not fit." to "N new in the list." when N > 0.
- R-B1 (read limit): `collect.profile` gets `readLimit` (new reads per run; 0 means no limit). Discover sets 200. `reread` and `readLimit` above 0 cannot be combined: `collect.profile`'s `validate` returns an error-level problem for the pair ("Re-read and a read limit cannot be used together."), so the run does not start; asserted in `packages/contracts/src/collectBlocks.unit.test.ts`. People read in the last `RECENT_DAYS` (30) are not paid again and do not count. Enriched people never count. People over the limit go under the block's Else key (flag `keepsAside`) and are not passed on.
- R-B1a (decided once): the cut is recorded as the step's Else items. On a pass after `Waiting`, the cut set is those items and the kept set is the inputs minus the cut set. With no cut, a later pass re-splits, but the new pool can only shrink (a read turns new into reused), so the total of new reads still stays within `readLimit`. A zero-cut test asserts it.
- R-B2 (ranking): a person's rank is the best of their `signals` (`PersonItem.signals`, each with `type` and `at`): `commented` 0, `reacted` 1, any other 2. A person's key is the newest `at` among the signals of that best rank (ISO strings compare as text; null last; ties by slug). Only the cut uses the ranking; `readPeople` still reads in slug order.
- R-C1 (Invite): starts with `trigger.workflow` naming the Discover workflow when a Discover id is given (no schedule then; without an id the old schedule stays), so Invite does not start an hour after Discover by clock. Both branches of the Invite graph (with and without a note) get the trigger. Its people input: `added: 'any'`, `invites: ['NONE']`, `howMany: 100`, `order: newest`, labels `[lead-<slug>]`. Warm up, First message and Hand off keep their clock times.
- R-C1a (chain): a finished Discover run that listed people starts the Invite run once. Only the engine's finish starts Invite: `WorkflowService.listeners` derives the listeners at finish from the saved graphs (enabled workflows of the owner whose `trigger.workflow` names the finished workflow; no registry), and `startAfter` starts each one once. The gate is the finish of a run in `engine.ts`: `startAfter` runs only when the run is the one that ended (`count === 1`), not failed or stopped, not a preview and kind `MAIN`; `WorkflowTriggerService.startAfter` (`workflowTrigger.service.ts`) returns 0 for an empty list of people; the engine passes the run's listed people from `engine.ts` (Discover has no Give back block, so the listed people apply). If an Invite run is live, the start queues (the queue rule in `admit` in `apps/brain/src/database/workflow.service.ts`, up to 10 queued). It is dropped silently when the queue is full, the Invite workflow has a problem, or the wallet is below its floor (`startAfter` swallows those errors); a dropped start is not retried, and the labelled people wait for the next Discover run that listed people.
- R-C2: Invite finds its people through `Person.labels` (Profiles input, network source). It does not use the payload that `trigger.workflow` passes.
- R-D1 (last Discover run): a new function `CampaignStatsService.lastDiscoverRun(userId, campaignId)`: the newest `WorkflowRun` of the owner whose workflow has this `campaignId` by `startedAt` and `stage` `DISCOVER`, with `trigger` not `PREVIEW` and `kind` `MAIN`; fields `status`, `startedAt`, `finishedAt`, `message`, `qualified`, `maybe`; a live run is included (`finishedAt` null). The existing `workflow.runs` select (used for the cards and the alerts) does not change. It returns `null` when the campaign is not the owner's, as `overview` does.
- R-E1 (backfill): Approach step 7 (SQL only, no schema change).
- R-F1 (Starter): Discover is created first; the other five use its id (Approach step 5).
- R-G1 (dedupe): Discover keeps the default dedupe (`skipListed` and `skipProfiles` on): a person already in any owner list or in `/profiles` is not read again. So `addFromRun` never receives a known person from Discover, and the `known` path is not used by this campaign. A person is in at most one list.
- R-H1 (Labels page): in `LabelService.list`, the people branch of the outer UNION becomes `SELECT d.label, 'people' AS kind FROM (SELECT DISTINCT x.label, x.slug FROM (SELECT unnest(m."tags") AS label, m."slug" FROM "WorkflowListMember" m JOIN "WorkflowList" l ON l."id" = m."listId" WHERE l."userId" = ${userId} UNION ALL SELECT unnest(p."labels") AS label, p."slug" FROM "Person" p WHERE p."userId" = ${userId}) x) d`, so it returns the same two columns as the other branches (label, kind). The outer query is unchanged (`GROUP BY label, kind`, `count(*)::int`). A person counts once per label across both sources and across two lists with the same label (the second case counts once now; it counted twice before; accepted). Profiles, companies and posts keep their branches unchanged.

Discover target graph (replaces the current Score, Profile, Score chain). Node ids, types, config:

- `trigger`: `trigger.schedule` (the time from the Starter's form).
- `find0` to `findN` (N + 1 = the number of phrases the Starter's answers give, 1 to 5): `collect.findPosts` (keywords: one phrase each; howMany: `ceil(postsPerDay / phrases)`, with postsPerDay 8 by default from the Starter's form; postedWithin `24h`; keep true, which keeps the posts in the owner's posts list).
- `posts`: `process.dedupe` (defaults).
- `commenters`: `collect.commenters` (howMany 50); `reactors`: `collect.reactors` (howMany 50).
- `people`: `process.dedupe` (defaults).
- `profile`: `collect.profile` (`readLimit` 200, `reread` false).
- `score`: `score.icp` (icpId); its kept output (qualified and maybe) goes to `label`; the others are counted as discarded.
- `label`: `process.tag` (tags: the campaign label from `campaignLabelOf`, of the form `lead-<slug>`).
- `list`: `output.list` with no config: it writes to the workflow's own output list (`Workflow.outputListId`). Each item keeps the `tags` set by Add label upstream; those are what `WorkflowListMember.tags` stores and what statement M backfills.
- `done`: `output.markPosts`.

Edges: trigger to each find; each find to posts; posts to commenters and to reactors; commenters and reactors to people; people to profile; profile to score; score to label; label to list; posts to done. The old `score2` node is removed.

Known residual (accepted, to be written in the Outcome): the campaign tags `control` (warm-up control) and `handed-off` are written as plain labels, so they are shared between campaigns. The warm-up control count and the hand-off exclusion can therefore cross campaigns. A person in two campaigns is already counted in each. Also accepted: a person deleted by the index in the same instant a label is written can lose that label (the index reads its row before deleting it; the window is a few milliseconds and needs a person with no rows and no labels).

New blocks: none. Considered and not added: a gate block (`trigger.workflow` already starts only when people were kept); a read-limit block (a setting on Get full profile is enough); a campaign-stage block (the Starter already builds the six stages).

Open questions: none. Answered by the owner on 2026-11-10:

- Scope of Decision 1: every campaign stage (labels are written by every stage of a campaign run, so Warm up's `control` and Hand off's `handed-off` counts work).
- Plan locked on 2026-11-10; execution follows the Approach steps in order, starting with step 1 (staging check, already recorded above).

## Edge cases and risks

- A failed list step: members are inserted before their labels are written, so a failure after the insert leaves members with no label. The run ends FAILED and no chained Invite starts. A later Discover run dedupes those people out (they are in a list), so it does not label them. The repair is `apps/brain/prisma/manual/campaign_labels_repair.sql`: idempotent, and it finds the members by `addedByRunId`. Run it by hand once after such a failure, and record it in the Outcome.
- Labels and the index: the index never writes `labels` (its update path does not touch the column), so the job and the label write cannot undo each other. One known gap: a person deleted by the index in the same instant a label is written can lose that label (the index reads its row before deleting it; the window is milliseconds and needs a person with no rows and no labels). Accepted.
- Label cap and order: existing labels are never removed or capped (manual labels included). Only the appended tags are capped, at `LABEL_MAX` minus the existing count. A tag that does not fit is dropped and counted in the run message. A person already at the cap does not get the campaign label; the count shows it.
- Known people: a person already in a list or in `/profiles` is skipped by dedupe (R-G1), so they are not labelled and not invited by this campaign.
- Race: a person labelled by `process.tag` or by the list step, and refused by `addFromRun`'s own check because another list took them in the same moment, keeps the label without a membership. Accepted; rare.
- `replacePrefix` (Add label) changes run items only; `Person.labels` keeps earlier labels. The Starter does not use `replacePrefix`.
- NULL `tags` add nothing (`unnest` of NULL returns no rows).
- Backfill is forward-only: no reverse statement removes the labels it added (one would also remove labels the owner or later runs added); accepted.
- Backfill: a rerun gives the same labels; it writes only the `labels` column; it relies on `Person` rows for those members (Approach step 1 checks it).
- Cost: Discover reads at most 200 new profiles a run, about $0.80 a day (one Discover run a day, the Starter's schedule) at $0.004 each, before reuse. Reused people are not paid and do not count. The estimate is an upper bound (`min(incoming, readLimit)`), not the exact new reads, and the wallet floor still stops a run.
- Read limit across passes: the cut is decided once and recorded as Else items (R-B1a), so a pass after `Waiting` cannot read a second 200.
- Leftovers over the limit sit under the Else key of the run only; they are not read later by this campaign.
- Invite backlog: Invite takes up to 100 labelled people per run (the block's `howMany`). A backlog above that waits for the next run that listed people. A day with no new people does not start Invite, so the backlog waits longer. Accepted for now; a later change can add a daily Invite run.
- Chain: Invite starts only after a Discover run that is not failed or stopped (a PARTIAL run still chains). A live Invite run queues the chained start (`admit` in `apps/brain/src/database/workflow.service.ts`, up to 10 queued). A start dropped for a full queue, a problem in the Invite workflow or the wallet floor is not retried (R-C1a; existing behaviour, no new test). The queue-full (`workflow.service.ts` line 152), Invite-problem (line 729) and wallet-floor (lines 737 and 834) refusals all throw `ConflictError`, the only error `startAfter` swallows; any other error escapes `finish` after the run is finished, as today. If Discover is off, Invite never runs; the Invite workflow shows that it runs after Discover.
- Idempotency: a repeated Discover run adds no duplicate labels; a chained start is keyed `<workflow>:after:<run>`, so one finished run starts Invite once.
- Existing behaviour, kept (`markPosts` in `executors.ts`): the last step marks posts processed when every other step is DONE (`markPosts` checks the steps, not the run status), even if nobody passed; those posts are not read again. The campaign page shows the run's count.
- Migration: SQL only, no schema change; safe to rerun.
- Security and privacy: labels are workflow tags; no names or message text in logs or run messages.
- Dev vs production: brain and brain-worker both run this code; the migration runs in the brain migrate init container before both start.
- Rollback is forward-only: code revert is not supported after phase 6 (a version 3 `collect.profile` block is not readable by version 2 code). Labels already added stay. To stop the new behaviour: set `readLimit` 0 in the block and switch Invite back to a clock trigger in the workflow.
- Residual (accepted): `control` and `handed-off` are shared between campaigns (see Requirements). The bulk label edit in `people.service.ts` writes labels without a cap or order (a follow-up).
