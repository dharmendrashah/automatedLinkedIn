# Project memory

Living notes for people and AI agents working on automatedLinkedIn. Read this before starting a task. When a task is done, update it (see "How to maintain this file"). Keep it short, factual, and current.

## How to maintain this file

- Add a decision, gotcha, or open item only if it would save the next person time. Do not log routine changes; git history does that.
- Edit or delete entries that are no longer true. Do not leave stale facts.
- One line per entry where possible; put the date on decisions and the changelog.
- Never store secrets, tokens, passwords, or the git remote URL here.

## Decisions

- 2026-10-11: LinkedIn credentials are stored encrypted per user for the tool to act as that login (own-account automation, in scope). Model `LinkedInAccount` (many per user, unique `(userId, email)`). Secrets (`password?`, `totpSecret?`, `session?`) live in one AES-256-GCM bundle in `secret`/`secretIv`/`secretTag` with `keyVersion`; boolean `hasPassword`/`hasTotp`/`hasSession` mirror presence so metadata reads never decrypt. `CryptoService` (`src/core`) does the sealing; the key is env `LINKEDIN_CRED_ENC_KEY` (base64 32-byte, validated at boot, `devDefault` for dev/test, **required in production**). tRPC `linkedInAccount` router (create/list/get/reveal/update/delete) under an `ownerProcedure` that scopes every call to `ctx.user.id`; `list`/`get` return metadata only, and only the explicit `reveal` **mutation** returns decrypted secrets to the owner. KMS and a body settings UI are follow-ups.
- 2026-10-11: Staging moved to GKE zonal `staging-asia` in `asia-south1-b`, next to the Cloud SQL instance (`34.100.231.12`, Mumbai). Query latency fell from ~241 ms to a few ms, and authentik discovery from 7–13 s to ~0.3 s. The old `us-central1` cluster was deleted. One `e2-standard-2` Spot node, ingress-nginx `hostNetwork`, cert-manager with `letsencrypt-prod`. The node IP changes when the Spot node is replaced, so DNS must be updated (a script is planned). The CI deploy job targets `GKE_CLUSTER=staging-asia`, `GKE_LOCATION=asia-south1-b`.
- 2026-10-10: Kubernetes manifests live in `deploy/` as Kustomize (`base` + `overlays/local` + `overlays/staging`). PostgreSQL is **not** deployed: staging uses an existing external server. Migrations run as an **init container** on the `brain` Deployment (not a Job), so `replicas` stays 1 with `strategy: Recreate`. Three subdomains (`app.`/`api.`/`auth.`), ~$21/mo. Per-overlay `config.env` and `secrets.env` are git-ignored; CI writes them back from the GitHub secrets `STAGING_CONFIG_ENV` and `STAGING_SECRETS_ENV`, which hold each file verbatim.
- 2026-10-11: Both apps expose `GET /health` (JSON: `status`, `service`, `commit`, `builtAt`, and `startedAt` on brain, with `Cache-Control: no-store`). `commit` and `builtAt` come from the image build args `GIT_SHA` and `BUILD_TIME`, which `staging.yml` sets from `github.sha` and the job's UTC time. Local and release builds report `unknown`. Confirm a deploy with `curl https://api.staging.elitale.com/health` and `curl https://app.staging.elitale.com/health`. Body serves it from a static file with an exact nginx `location =`, so the SPA fallback is unchanged.

- 2026-10-10: authentik (pinned `2026.8.3`, no Redis) is the identity provider. It shares the single `postgres:18-alpine` service; its own `authentik` database and role are created on first init by `infra/postgres/init/10-authentik-db.sh`. `body` signs in with OIDC code flow + PKCE as a public client (`oidc-client-ts`, `react-oidc-context`, tokens in sessionStorage). Provider, application and the sign-up flow come from `infra/authentik/blueprints/automatedlinkedin.yaml`, mounted into the worker. Sign-up is open self-registration without email verification. Brain verifies the access token (see next entry).
- 2026-10-10: Brain authenticates API calls with authentik access tokens: `jose` checks RS256 signature, issuer, audience (= client id) and expiry against authentik's JWKS (`src/auth`). `userProcedure` (tRPC) rejects with `UNAUTHORIZED` otherwise; `ctx.auth` is `{ token, sub }` and `ctx.user` is the local `User` linked by `User.authentikId` (= token `sub`). Brain creates the local user just-in-time: on a caller's first request `userProcedure` provisions it (`UserService.provisionAuthentikAccount`: find by `authentikId`, else link a row by email only when authentik reports `email_verified` true, else create one with the authentik email and name, role `USER`). An email already used by an unlinked row is never linked or duplicated (case-insensitive) and fails with `CONFLICT`; an identity without an email gets no row. `me` returns `{ identity, user }`. Everyone is `USER` (no group to role mapping). Without email verification, whoever signs up first with an address owns that row (email squatting).

- 2026-10-11: RabbitMQ runs locally (compose service `rabbitmq`, UI http://localhost:15672) and in staging/minikube as a single-replica StatefulSet in `deploy/base` (2Gi PVC, ClusterIP only, uid 100, no read-only root). Brain reads `RABBITMQ_URL` (required in production; the vhost is `automatedlinkedin`) and `MessageBroker` (`src/core`) keeps one lazy shared connection; `/health` reports `broker: up|down` but only the database gates readiness. In Kubernetes brain builds the URL from the broker's own two secret keys (`RABBITMQ_DEFAULT_USER`/`RABBITMQ_DEFAULT_PASS`, URL-safe password) with `$(VAR)` expansion. No queues or consumers exist yet.

- 2026-10-11: `apps/spider` is a local-only asynchronous scraper (not deployed to staging, not in the publish matrices). Fastify API (internal, loopback in compose) queues a typed `ScrapeTaskCommand` on RabbitMQ (`scraping.exchange` -> quorum queue `linkedin.requests`, key `linkedin.task`); a Camoufox worker (since 2026-10-12, replaces Playwright's Chromium) takes one task at a time (`prefetch(1)`), runs the actions in a fresh Camoufox, writes raw JSON to the GCS bucket `gs://automate-linkedin-511215-spider` (`results/`), publishes a `ScrapeTaskResult` (`task.result`) and acks only after both (late ack). Controls: only hosts in `SPIDER_ALLOWED_HOSTS` (local default now includes `linkedin.com`, on the operator's attestation of LinkedIn's permission, see `.plan/camoufox-browser.md`), `robots.txt` honoured except for `SPIDER_ROBOTS_EXEMPT_HOSTS` (local default `linkedin.com`, because LinkedIn's robots.txt disallows every unlisted agent), a fixed per-host gap, cookies only for allowed hosts, a 4xx/5xx is a failure never worked around. Accounts: a command may carry `account_id` and `proxy` (credentials inline in the message, `geoip` follows the proxy, a bad proxy fails the task and never falls back to a direct connection). With an `account_id` the worker loads `sessions/<account_id>/state.json` (cookies only; `auth_session_key` only seeds a new account), takes a per-account lease (`locks/<account_id>.json`, GCS generation preconditions, `SPIDER_ACCOUNT_LOCK_TTL_MS` 30 min, no heartbeat), and after a successful task writes the refreshed cookies back and returns only `session_storage_path` in the result; a busy account is re-queued after `SPIDER_ACCOUNT_BUSY_DELAY_MS` without using a retry. Run it with `docker compose --profile spider up -d spider-api spider-worker` (needs `SPIDER_GCS_BUCKET` and ADC), or `pnpm --filter @automatedLinkedIn/spider dev` / `dev:worker`.

## Gotchas

- RabbitMQ 4.3 quorum queues redeliver `nack(requeue=true)` instantly and do NOT count it toward `x-delivery-limit`, so a failing consumer spins (about 100 attempts a second). Spider retries by publishing a copy with an `x-retries` header after a back-off and dead-letters after 3 retries; never use nack-requeue as a retry loop.
- Application Default Credentials are per machine and may belong to a different Google account than `gcloud`'s active one (here ADC was another organisation's account), so a worker can reach GCS and still get `storage.objects.create denied`. Check with `gcloud auth application-default print-access-token` or the error text. To keep other work untouched, log in to a separate ADC file: `CLOUDSDK_CONFIG=$HOME/.config/gcloud-spider gcloud auth application-default login`, then point `GOOGLE_APPLICATION_CREDENTIALS` (local) or `SPIDER_GCP_CREDENTIALS` (compose) at `$HOME/.config/gcloud-spider/application_default_credentials.json`.
- `camoufox@0.5.8` has the peer `playwright-core` `<1.63`, so spider pins `camoufox` and `playwright-core@1.62.0` exactly and must not use the 1.64 Playwright image (the worker image is now `node:25-bookworm-slim` plus Firefox libraries and `camoufox fetch`). `camoufox` is ESM-only but `require('camoufox')` works on Node 25. The browser build is 1.29 GB (about 2.5 GB unpacked) in `~/Library/Caches/camoufox` (macOS) or `~/.cache/camoufox`; `pnpm --filter @automatedLinkedIn/spider exec camoufox fetch` takes about 15 minutes and prints no progress without a TTY. Real-browser tests need it and take about 2.5 minutes: `pnpm --filter @automatedLinkedIn/spider exec vitest camoufoxDriver.e2e.test.ts --run --testTimeout=120000`.
- In this Cursor/VS Code agent shell, `pnpm exec <bin>` run from the repo root does not find package binaries; use `pnpm --filter @automatedLinkedIn/spider exec ...` (or `cd` into the package).

- Kubernetes: `app-secrets` is generated with a content hash in its name, so changing `STAGING_SECRETS_ENV` creates a new Secret and rolls every workload. A StatefulSet pod that is stuck (for example `CreateContainerConfigError` from a missing secret key) is NOT replaced by the rollout, because a StatefulSet waits for the old pod to become Ready. After fixing the secret, delete the stuck pod (`kubectl -n automatedlinkedin delete pod rabbitmq-0`); its PVC is kept. Seen on 2026-10-11 when staging was deployed before `LINKEDIN_CRED_ENC_KEY` and the RabbitMQ keys were in the secret: brain crash-looped on the missing key and `rabbitmq-0` stayed stuck.
- Every new required production env var (no `devDefault`) must be added to `STAGING_SECRETS_ENV` (or `STAGING_CONFIG_ENV`) before the PR that needs it is merged, because merging to `main` deploys staging immediately. Set it with `gh secret set STAGING_SECRETS_ENV < deploy/overlays/staging/secrets.env` after adding the key to the local git-ignored file. `STAGING_SECRETS_ENV` now holds `LINKEDIN_CRED_ENC_KEY`, `RABBITMQ_DEFAULT_USER` and `RABBITMQ_DEFAULT_PASS`.

- A brain unit test that imports the real `trpc` (for `router`/`userProcedure`) pulls in `trpc.ts` → `./api/identity` (a value import) → `auth` → `env`, so envalid runs `cleanEnv` and calls `process.exit(1)` if `DATABASE_URL` is missing (there is no committed `.env.test`). Such tests must `vi.mock('env', ...)` with a full env object (see `router.unit.test.ts` and `linkedInAccount.unit.test.ts`). Tests that mock `./identity` (like `me`) avoid loading `env` entirely because trpc.ts imports `Context` as a type only.
- brain is CommonJS (`module: commonjs`), so top-level `await import(...)` is a TS1378 error. Use static imports in tests; `vi.mock` is hoisted above them anyway. A class referenced inside a `vi.mock` factory must be declared inside `vi.hoisted` (not a plain top-level `class`), or it hits the temporal dead zone.
- `object-curly-newline` (brain ESLint) fights Prettier on a single-key object that Prettier is forced to wrap because the line exceeds 120. Fix by shortening the line (zod `.refine(pred, 'message')` string form, or a block body returning `{ key }`) rather than fighting the formatter.
- The `add_linkedin_account` migration was hand-written (no database was reachable at the time). It was later applied locally and `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` reported no drift, so the hand-written SQL matches Prisma. Use that diff command to check any hand-written migration.
- shadcn CLI repeated the `from "cn"` bug for `dialog` and `alert-dialog`; after any `shadcn add`, grep `src` for `from 'cn'` / `from "cn"` and rewrite to `@/lib/utils`, and check `package.json` for a stray `cn` dependency.
- `LinkedInAccountStatus` is `PENDING | ACTIVE | NEEDS_REAUTH | ERROR | DISABLED` (columns `status`, `statusMessage`, `statusUpdatedAt`, `lastVerifiedAt`). Only the owner's pause/resume (`setPaused`, `DISABLED` <-> `PENDING`) is reachable through the API; ACTIVE/NEEDS_REAUTH/ERROR are reserved for a future server-side verify worker, which must skip `DISABLED` accounts. Changing an account's secrets resets a non-disabled account to `PENDING` and clears `lastVerifiedAt`.
- `.plan/linkedin-account-linking.md` (draft) blocks any LinkedIn login/automation code until LinkedIn's written permission (B1) is confirmed, and warns that a stored TOTP seed lets a service generate codes forever. The credential storage and status/table work only store and display metadata and do not log in to LinkedIn; the B1 decision and the TOTP-seed question are still open there.

- Brain resolves top-level `src` folders as bare imports through `module-alias`. `./aliases` must load before them. A new top-level folder must be added to `importOrder` in `.prettierrc`, or `lint:fix` hoists its import above `./aliases` and production crashes with "Cannot find module".
- TypeScript 7 removed `baseUrl` and `moduleResolution: node10`, and no longer auto-loads `@types/*`. `typescript-eslint` needs TypeScript 6, pinned only in `packages/eslint-config`.
- A default import of `module-alias` has no types; use `import { addAliases } from 'module-alias'`. In tests mock it with `vi.mock`, not `vi.spyOn`.
- `apps/brain/vitest.config.mts` must stay `.mts` (`vite-tsconfig-paths` is ESM-only, brain is CJS).
- Anything imported at runtime by brain must be in `dependencies`; the image installs production dependencies only. `packages/config` ships only `dist`. `pnpm deploy` needs `--ignore-scripts` because `postinstall` runs `prisma generate`.
- Express 5 rejects the bare `'*'` route; use `'/{*splat}'`.
- `apps/body` type-checks brain source through its `AppRouter` import, so it needs the `trpc` and `trpc/*` path mappings in `tsconfig.app.json`.
- Long Docker commands run in a sync terminal can swallow output. Run them async with output redirected to a `/tmp` log, then read the log.
- zsh: never put a literal `!` in a commit message.
- The compose Postgres holds three databases: `automatedlinkedin` (compose `brain`), `postgres` (default; also migrated so local `pnpm dev` can use `DATABASE_URL=.../postgres`) and `authentik`. A database only gets the app tables after `DATABASE_URL=... pnpm --filter @automatedLinkedIn/brain db:migrate:deploy`; from the host use `localhost:5432`, the `postgres` host name only works inside compose.
- `express-serve-static-core` in brain's `dependencies` is a stub package ("only here to make types work"); it makes `Request` lose its `http` members (`req.headers`, `req.get`). `createContext` types the headers by hand. Fixing it means replacing the stub with `@types/express-serve-static-core`.
- `apps/body` must import brain's `AppRouter` with `import type { ... }`, not `import { type ... }`: with `verbatimModuleSyntax` the latter leaves a side-effect import, so Vite loads brain's server code and fails on its bare imports (`auth`, `trpc`, ...).
- Brain's access-token key set (`AuthService`) is memoised per JWKS URL; a unit test that checks the URL must be the first `authenticate` call in the file.
- authentik flows only accept a relative `next` (absolute URLs fail with "Invalid next URL" when the flow finishes). Sign-up therefore builds the OIDC authorize URL first (`AppUserManager.createSigninUrl` in `apps/body/src/auth/userManager.ts`, which also stores the PKCE state) and passes its path and query as `next`.
- authentik compose secrets (`AUTHENTIK_SECRET_KEY`, `AUTHENTIK_PG_PASS`) have public dev defaults on purpose (a required-variable error would break `docker compose up postgres`). Never reuse them outside local development. Set real values in the root `.env` (see `.env.example`).
- Redirect URIs in the blueprint are hard-coded to `localhost:3000` and `localhost:5173`; a deployed host needs the blueprint and `VITE_AUTHENTIK_*` build args changed.
- Building `deploy/` needs `kubectl kustomize --load-restrictor LoadRestrictionsNone deploy/overlays/staging`: the base reads the authentik blueprint from `infra/`, outside the kustomize root, to avoid a committed copy. It also needs `config.env` and `secrets.env` to exist in the overlay (both git-ignored); copy the `*.example.env` files first or the build fails.
- GCP project `automate-linkedin-511215` enforces `constraints/iam.disableServiceAccountKeyCreation`, so `gcloud iam service-accounts keys create` fails with `FAILED_PRECONDITION`. CI authenticates with Workload Identity Federation instead (no stored key). The provider's `--attribute-condition` pinning `assertion.repository` is the security boundary — without it any GitHub repo could impersonate the service account.
- `deploy/overlays/local` runs the whole stack on minikube against the compose PostgreSQL (`host.minikube.internal`, needs `infra/local-k8s/postgres-expose.yml` because compose binds Postgres to `127.0.0.1`). Verified working: see `deploy/local.md`. Two traps: the cluster and compose share one authentik database, so the compose `authentik-worker` must be stopped or it overwrites the blueprint's redirect URIs; and images must be built before `minikube start`, since Docker Desktop's ~8 GB VM gets OOM-killed building next to a running cluster.
- Kubernetes `runAsNonRoot` needs a numeric `runAsUser`. The brain image declares `USER node`, which kubelet cannot verify, so the Deployment sets `runAsUser: 1000` (the `node` user). Without it the container fails with `CreateContainerConfigError`.
- Images built on an Apple Silicon Mac are `linux/arm64` and GKE nodes are `linux/amd64`; pulling one gives `no match for platform in manifest`. Build manually with `docker buildx build --platform linux/amd64 --push`. CI is already correct (`platforms: linux/amd64`).
- Prisma and authentik both create their own tables, so each needs `CREATE` on its database's `public` schema; connect permission alone fails with `permission denied for schema public`. On the staging Cloud SQL instance both databases are owned by `postgres`, and `anpr_user` has neither ownership nor role memberships.
- GHCR packages are private by default, so the cluster cannot pull `-brain`/`-body` without credentials. The staging overlay adds `imagePullSecrets: [ghcr]` to those two Deployments, and the deploy job creates that secret from the `GHCR_PULL_TOKEN` PAT (`read:packages`). `GITHUB_TOKEN` is not used for it, because it expires with the job and a later node replacement could no longer pull.
- authentik needs `CREATE` on the `public` schema of its database; a role that can only connect is not enough, because it runs its own migrations. `AUTHENTIK_POSTGRESQL__NAME` is the database and `__USER` is the role — swapping them fails with `password authentication failed for user "<database name>"`.
- `deploy/.gitignore` scopes the ignores to `overlays/*/config.env` and `overlays/*/secrets.env`. A bare `config.env` rule would also swallow `deploy/base/config.env`, which holds the shared non-secret defaults and must stay committed.
- The authentik blueprint's redirect URIs and `meta_launch_url` come from `!Env [APP_URL]` (no trailing slash) via `!Format`, defaulting to `http://localhost:3000`. The `localhost:5173` vite entries are still hard-coded. A deployed host sets `APP_URL`; the `VITE_AUTHENTIK_*` build args still have to match, because the SPA bakes them at build time.
- `apps/body` bakes `VITE_*` at build time, so its image is environment specific. `.github/workflows/staging.yml` builds a separate `staging`-tagged image from the repository variables `STAGING_API_URL` and `STAGING_AUTH_URL`; changing a URL means a rebuild, not a config change.
- `infra/postgres/init/*` runs only when the `postgres` data volume is first created, so the `authentik` database is not added to a volume that already exists. On an existing volume create it by hand: `docker compose exec -e PGPASSWORD=postgres postgres psql -U postgres -c "CREATE ROLE authentik LOGIN PASSWORD 'authentik'" -c "CREATE DATABASE authentik OWNER authentik"`, then inside it `ALTER SCHEMA public OWNER TO authentik;`. It also never runs for Kubernetes, where the database is external and must be prepared by hand.
- authentik blueprint: identify the `oauth2provider` by `client_id` (unique), not `name`. If a provider with that client_id already exists (e.g. the UI's "Provider for <app>" default), a `name` identifier makes the importer try to insert and fail with a client_id unique error, which aborts the whole blueprint (status `error`, no flow created, flow URL shows "Not Found").
- authentik blueprint: when updating the default `default-authentication-identification` stage to add an `enrollment_flow`, also set `user_fields` (e.g. `[username, email]`), or it fails validation "When no user fields are selected, at least one source must be selected".
- Blueprint apply errors are silent in the UI. Diagnose with `docker compose exec authentik-worker ak apply_blueprint custom/automatedlinkedin.yaml`; check `select name, status from authentik_blueprints_blueprintinstance`.
- authentik blueprint: the OIDC provider must set `grant_types` (`authorization_code`, `refresh_token`). Left empty, every authorize request fails with "The request is otherwise malformed" (log: "Invalid grant_type for provider"), even though discovery looks correct.
- authentik sign-up verification and password reset send mail through Resend over SMTP (`AUTHENTIK_EMAIL__*`, host `smtp.resend.com`, port 465 SSL, username `resend`, password = API key in `secrets.env`). Sign-up accounts start inactive and are activated by the verification link, so do NOT apply the blueprint to an environment until its SMTP settings work, or new sign-ups get stuck.
- Local mail: `docker compose` runs a `mailpit` catcher (UI http://localhost:8025). authentik sends to it by default (`AUTHENTIK_EMAIL__HOST=mailpit`), so no real mail leaves the machine. To send through Resend locally, set the `AUTHENTIK_EMAIL__*` values in `.env` (see `.env.example`). Kubernetes is unchanged.
- Staging DNS: a CronJob (`overlays/staging/dns/`, every 5 minutes) keeps `app.staging.elitale.com` (DNS only, TTL 60) pointed at the node's external IP, read from the GCE metadata server. `api.` and `auth.` are CNAMEs to `app.`. It needs the GitHub secret `CLOUDFLARE_API_TOKEN` (Zone DNS Edit on elitale.com) and the zone ID in `kustomization.yaml`. Until both are set, the job fails and DNS does not change.
- authentik enrollment: the user-write stage must set `user_type: internal`, or sign-ups are created as `external` and get "Permission denied — Interface can only be accessed by internal users" on `/if/user/` (the "Manage account" link). Fix an existing external user with `update authentik_core_user set type='internal' where ...`.

- `apps/body` UI is Tailwind v4 + shadcn/ui (`components.json`, `@/` alias set in Vite and both tsconfigs; it does not collide with brain's bare aliases). Add components with `pnpm dlx shadcn@latest add <name>` from `apps/body`. The CLI mis-detected the utils import: it wrote `from "cn"` in generated files and added a bogus `cn` npm dependency. Fix by rewriting those imports to `@/lib/utils` and removing the `cn` dep. Dark mode is the `.dark` class driven by `next-themes` (system by default). Generated shadcn files produce oxlint warnings (react-refresh exports); leave them.
- `apps/body` routes: `PublicLayout` (`/`, `/login`, `/signup`, `/callback`) and `DashboardLayout` (`/dashboard`, `/accounts`, `/profile`, wrapped in `RequireAuth`). Profile data is read-only in the SPA; editing goes to authentik (`authConfig.accountUrl`). `/accounts` (sidebar: "LinkedIn accounts") is a shadcn table of the user's stored LinkedIn logins (columns: account, status badge, credentials, last verified, added, actions) with an "Add account" dialog on top. Row actions: reveal credentials (on-demand dialog; secrets cleared on close), pause/resume, remove (alert dialog). Components live in `src/components/accounts/`.
